# 需求澄清框架（WHY → WHAT → HOW）

阶段一使用。目标是把模糊想法变成清晰的产品决策。**每一步等用户确认后再进下一步，不跳步。**

用户一上来就跳到 HOW（直接说实现方案）时：先肯定其思路，然后说明「先把 WHY 和 WHAT 对齐，后面 HOW 的讨论才有锚点」，温和地拉回来。

---

## 0. 澄清结论的落点（撰写补充说明时必读）

本框架产出的结论**不在正文呈现**，按下列落点分流。撰写阶段四时据此回填。

| 澄清产出 | 最终落点 |
| :--- | :--- |
| WHY 三句话、现状与痛点、规模 | 补充说明 §2.1 业务现状与痛点 |
| 目标用户、受益方与操作方 | 补充说明 §2.2 目标用户与使用角色 |
| 需求目标 | 补充说明 §2.3 需求目标 |
| 北极星 / 辅助 / 护栏指标与目标值 | 补充说明 §2.3 成功标准 |
| 输出打样（类型 A）、影响面地图（类型 D）、现状审计（类型 E） | 正文（打样见方向 S 附录 A；影响面与审计转为正文规则） |
| MVP 分期 v1 / v2 与启动条件 | 正文「项目规划」或「范围与边界 → 明确不做」 |
| 衡量设计的验证问题、埋点清单 | 正文「数据与埋点」 |
| HOW 检查的模块划分、接口、边界、扩展预留 | 正文对应章节 |

**约束**：正文不得出现背景铺陈、痛点、目标用户、成功标准、指标目标值。这些只进补充说明。

---

## 1. WHY —— 对齐目标

用 1 轮对话搞定「为什么要做这个」。问三个问题：

(1) 这个功能 / 改造给谁用？他现在怎么解决这个问题？

(2) 现在的方式有什么痛点？

(3) 做完之后，情况会怎么变？（用户行为 / 系统表现 / 团队效率——取决于需求类型）

然后把回答整理成 **3 句话的 WHY**，让用户确认。不展开、不加修饰，就是 3 句话。

```
[谁] 现在用 [什么方式] 完成 [什么事]，耗时 / 出错 / 成本 [具体代价]。
痛点是 [具体问题]。
做完后 [谁] 的行为 / 系统表现会发生 [可观测的变化]。
```

**用户答不清「给谁用」时**：这本身就是有价值的信息。不要硬凑，把 WHO 标记为待定，WHY 写成「围绕 X 存在机会 / 问题，具体用户群待定」。这会在第 2 步自动导向类型 C。

---

## 2. 需求类型路由

WHY 确认后，判断属于哪种类型，**告诉用户你的判断并确认**。

| 类型 | 识别特征 | WHAT 的核心动作 |
| :--- | :--- | :--- |
| **A · 用户功能** | 有明确的最终用户、有界面 / 交互 / 可感知的输出 | 输出打样 |
| **B · 技术 / 平台能力** | 用户感知间接，核心是系统能力（API、算法、基础设施） | 成功指标 + 接口契约 |
| **C · WHO 模糊** | 连给谁用、解决谁的问题都不确定 | 用户画像澄清 → 再回到 A 或 B |
| **D · 系统性改造** | 跨多个模块 / 触点的整体改动 | 影响面地图 + 逐触点定义变化 |
| **E · 删减 / 简化** | 目标是减少复杂度而非增加功能 | 现状审计 + 取舍决策 |

**混合类型**：一个需求可能同时涉及多种类型（如「新功能 + 系统改造」）。此时告知用户识别到多种类型，建议按主线类型推进 WHAT，过程中兼顾其他类型的关键动作。

路由判断说法示例：

> 「根据你的描述，这是一个**用户功能**类需求——有明确的使用者，核心是他们看到什么、怎么交互。我按这个路径推进 WHAT，你看对吗？」

> 「这个需求我判断是 **A（用户功能）+ D（系统改造）** 的混合——既要做新的用户界面，又涉及底层数据流的整体迁移。建议以用户功能为主线推进，同时在场景穷举时把改造的影响面覆盖进来。你觉得呢？」

### 与特化方向的关系

需求类型（A–E，本节）回答「按什么思路想」；特化方向（S 通用软件 / A Agent 类，见 `../SKILL.md` §2）回答「文档按什么骨架写」。**两者正交，先定类型，再定方向。**

---

## 3. WHAT —— 按类型分支推进

### 类型 A：用户功能

**a. 输出打样**

根据用户描述，直接给出一个**最终用户会看到的输出示例**（界面 / 文案 / 消息 / 页面 / 报告）。

不要问用户格式偏好，先出一版让用户改——用户看到具体的东西才能判断好不好。打样确认内容结构后，同时确认输出的风格 / 密度 / 语气是否符合使用场景（如：紧凑 vs 详细、纯文字 vs 结构化卡片、客观描述 vs 带建议）。

**b. 场景穷举**

输出示例确认后：

(1) 问用户这个功能有几种不同的触发场景或用户状态

(2) 用表格列出所有场景组合，逐个确认每个场景下用户看到什么

(3) 主动提醒可能遗漏的边界场景（空状态、异常状态、首次使用、极端数据）——完整清单见 `shared/exception-handling.md` §3

(4) **边界规则必须标注适用场景**：定义了过滤、去重、截断等规则时，逐条标明在哪些场景生效、哪些不适用

**c. 信息取舍**

对着输出示例逐个信息项问：

(1) 这个信息用户需要吗？去掉会影响他做决策 / 行动吗？

(2) 能不能合并 / 简化？

目的是一次性锁定信息项，避免后面反复改。用户对信息密度敏感时宁少勿多。

**d. 锁定 WHAT**

把场景输出示例 + 信息项规则整理成文档让用户确认，然后明确告知：「WHAT 已锁定，接下来进入 MVP / 分期步骤。」

---

### 类型 B：技术 / 平台能力

**a. 定义成功指标**

这类需求没有「界面」可以打样，核心是定义「做好了长什么样」。问用户：

(1) 这个能力做好之后，怎么衡量它成功了？（延迟降到 X ms？准确率到 Y%？支撑 Z QPS？）

(2) 谁来判断它好不好？（用数据说话还是需要人评估？）

整理成 2–3 个可衡量的成功指标让用户确认，表结构见 `shared/metrics-spec.md`。

**b. 消费方与接口**

列出谁会调用这个能力，每个消费方的诉求：输入什么？期望得到什么？对响应时间 / 格式 / 错误处理有什么要求？

**c. 约束条件穷举**

性能、容量、兼容性、安全、成本——逐个确认。

**d. 锁定 WHAT**

WHAT = 成功指标 + 接口契约 + 约束条件。

> 注意：B 类在 WHAT 里已经定义了「成功长什么样」（目标值）。第 5 步衡量不重复定目标，而是解决「怎么追踪验证这些目标」。

---

### 类型 C：WHO 模糊

**a. 列出候选用户群**——不超过 3 个假设，每个说清：这是谁？场景是什么？他现在怎么解决？

**b. 让用户选定**——先做哪个群体？还是需要分别做？

**c. 回到 A 或 B**——选定后按需求性质回到对应路径继续。

---

### 类型 D：系统性改造

**a. 影响面地图**——列出所有触点：

| 触点 | 影响内容 | 受影响用户 |
| :--- | :--- | :--- |
| [模块 / 页面 / 接口] | [改前 → 改后] | [用户群] |

重点检查：哪些模块 / 页面 / 接口受影响？哪些用户群感知到变化？有没有下游依赖（其他系统读你的数据 / 调你的接口）？

**b. 逐触点定义变化**——每个触点：改前是什么样 → 改后是什么样。

**c. 迁移策略**——一步切还是渐进式？老数据 / 老接口怎么处理？需要灰度 / 开关吗？

**d. 锁定 WHAT**——WHAT = 各触点变化清单 + 迁移策略。

---

### 类型 E：删减 / 简化

**a. 现状审计**——把当前有的东西列出来，每项标注使用频率与对核心任务的贡献：

| 功能项 | 使用频率 | 核心任务贡献 | 建议 |
| :--- | :--- | :--- | :--- |
| [功能] | 高 / 中 / 低 / 极低 | 必要 / 辅助 / 可有可无 | 保留 / 合并 / 降级 / 砍掉 |

不要自己猜数据，问用户要或一起估算。

**b. 取舍决策**——逐项和用户确认：保留 / 合并 / 砍掉。

**c. 影响评估**——砍掉的东西现在有多少人在用？需要迁移方案吗（数据迁移、替代方案告知）？需要过渡期吗？

**d. 锁定 WHAT**——WHAT = 简化后的全貌 + 被砍项的处理方案。

---

## 4. MVP / 分期

WHAT 描述的是「完整理想态」，通常不可能一次做完。本步决定 v1 做什么、v2 做什么。

**4a. 标记优先级**

| 场景 / 能力 | 用户价值 | 实现成本（粗估） | 分期 |
| :--- | :--- | :--- | :--- |
| [能力] | 高 / 中 / 低 | 高 / 中 / 低 | v1 / v2 |

判断依据：
- **用户价值**：对 WHY 里的痛点贡献多大
- **实现成本**：粗估即可，高 / 中 / 低够用
- **依赖关系**：有没有「必须先做 A 才能做 B」

**4b. 定义 v1 范围**

v1 的标准是：**用最小范围验证 WHY 里的核心假设**。问用户：

(1) 如果只做这些，能不能验证「痛点确实被解决了」？

(2) 有没有哪个被砍到 v2 的东西其实是 v1 必须有的？

**4c. 规划 v2 及后续**

按逻辑分组排出 v2 要做的事，内容多可粗排 v3。不需要精确排期，只需明确「先后顺序和分组逻辑」。

确认后告知：「范围已锁定。v1 做 X，v2 做 Y。」

---

## 5. 衡量设计

针对 v1 范围，定义「做完之后看什么来判断成功」。

先判断走完整版还是轻量版：

| 特征 | 完整版 | 轻量版 |
| :--- | :--- | :--- |
| 面向大量外部用户 | ✓ | |
| 需要 A/B test 验证效果 | ✓ | |
| 行为数据丰富，可量化 | ✓ | |
| 内部工具 / 给少数人用 | | ✓ |
| 规则确定性系统（输出可预测） | | ✓ |
| 早期 MVP，先验证可用性 | | ✓ |

告知用户判断结论与理由，确认后按对应路径推进。

### 轻量版

(1) 定义 2–3 个核心验证问题（如：「用户用不用？」「结果准不准？」「省没省时间？」）

(2) 每个问题确认怎么获得答案：埋点采集 or 定期人工访谈

(3) 确认验证节奏（上线一周后评估？两周？）

### 完整版

**5a. 北极星指标**——问用户：这件事做完，你最关心哪**一个**数字的变化？从模糊表述收敛到一个可衡量指标。用户说不出来时给 2–3 个候选让其选择。收敛方式见 `shared/metrics-spec.md` §3。

**5b. 辅助指标 + 护栏指标**——辅助 1–2 个从不同角度确认效果；护栏 0–1 个回答「什么东西不能变差」。没有就不强加。

**5c. 数据埋点设计**（方向 S 必做，方向 A 按需）

| 事件名 | 触发时机 | 关键属性 | 对应指标 |
| :--- | :--- | :--- | :--- |
| `[event_name]` | [何时触发] | [属性列表] | [指标名] |

用户不关心埋点细节时，简化为「需要追踪哪些关键行为」即可，不强塞技术细节。

**5d. 判定标准**——数字到多少算成功？观察多久做判定？没达标怎么办（迭代 / 砍掉）？

确认后告知：「衡量标准已锁定，接下来进入 HOW。」

## 6. HOW —— 定实现逻辑（针对 v1）

进入前先提醒用户：

> 「现在讨论的是 v1 的实现方案，不会改变前面锁定的 WHAT 和衡量标准。如果讨论中发现需要改，先明确退回对应步骤。」

**退回规则**：需要改 WHAT、范围或衡量标准时，不必从头来。告知用户「需要退回 X 改一下 Y」，改完受影响部分后重新锁定即可。

按以下顺序推进：

(1) **输入**——实现 v1 需要哪些输入？从哪里获取？

(2) **核心处理逻辑**——从输入到输出，核心处理逻辑是什么？多方案时列对比表让用户选。

   - **逐场景确认**：WHAT 定义了多种场景时，必须逐个场景确认其计算 / 挑选 / 排序逻辑，不要假设所有场景用同一套规则。特别注意不同场景下「选哪些数据进入展示」和「怎么排序」可能完全不同。
   - **公式必须写全**：涉及计算的地方（排序分值、阈值判定、贡献度等）必须写出完整公式（含分子分母和运算符），不能用「变化率」「贡献度」等自造词代替。
   - **同类公式横向一致性检查**：多个分组 / 场景各有一套公式时，横向对比检查各公式考虑的维度是否对齐，有没有某组遗漏了本该考虑的因子。逻辑不对称时主动指出并确认。
   - **判断是否需要流程图**：存在多步骤条件分支、多角色协作交接、循环 / 重试 / 异常回退、状态机时，**必须**产出流程图（Mermaid）。单一链路无分支的线性流程（如：拉数据 → 计算 → 输出）不需要画图，用模块划分说清即可。

(3) **模块与角色**——有哪些模块 / 角色？各自的职责边界？

(4) **模块间接口**——输入输出的数据结构怎么定义？

(5) **边界情况**——无数据、异常值、超时、权限等怎么处理？（逐类对照 `shared/exception-handling.md` §1）

(6) **埋点落地**——衡量步骤定义的埋点在实现中怎么落地？哪个模块负责上报、数据流向哪里？

(7) **v2 扩展预留**——v1 的设计有没有为 v2 留好扩展空间？不过度设计，但明显的扩展点要标出来。

## 7. 检查清单

全部想完后，用以下清单检查，发现问题指出**具体哪里有问题并建议怎么改**，不要只说「这里不够好」。

### 通用项

- [ ] WHY：一个不懂背景的人看完能理解为什么要做吗？
- [ ] WHAT 和 HOW 有没有混在一起？能清晰分开吗？
- [ ] HOW 能覆盖 WHAT 里的所有场景 / 触点 / 接口吗？
- [ ] 衡量指标能直接验证 WHY 里的痛点是否被解决了吗？
- [ ] 边界情况都处理了吗？
- [ ] 整体读一遍，有没有前后矛盾的地方？
- [ ] Mermaid 流程图是否都能正常渲染？
- [ ] 所有公式是否含分子分母与运算符？

### 类型专属项

| 类型 | 检查项 |
| :--- | :--- |
| A · 用户功能 | 每个场景都有输出示例吗？有没有遗漏的场景？信息项是最少够用的吗？ |
| B · 技术 / 平台能力 | 成功指标可衡量吗（不是「更好」「更快」）？接口定义能覆盖所有消费方诉求吗？ |
| C · WHO 模糊 | 候选用户群是否已收敛到明确对象？选定后是否已回到 A 或 B 路径？ |
| D · 系统性改造 | 影响面地图有没有遗漏触点？迁移策略覆盖了所有存量数据 / 用户吗？ |
| E · 删减 / 简化 | 砍掉的功能有用户会被 break 吗？有处理方案吗？ |

### 分期 / 衡量专属项

- [ ] v1 能独立验证 WHY 的核心假设吗？不会做完了还是看不出效果？
- [ ] 有没有把「低成本但高价值」的东西漏到 v2 了？
- [ ] v2 的内容是否有明确的启动条件（v1 达到什么指标后启动）？
- [ ] 北极星指标和 WHY 的痛点直接挂钩吗？
- [ ] 有没有可能指标涨了但用户实际体验没变好？（虚荣指标风险）
- [ ] 埋点能覆盖所有需要计算的指标吗？

## 8. 交互规则

这些规则用于适配用户「边做边想」的认知风格——需要看到具体的东西才能推进。

(1) **每次只讨论一个问题**——多个选择同时出现会让用户卡住。

(2) **先给具体示例让用户改，不要让用户从零描述**——每种类型的 WHAT 阶段都先出一版具体的东西，让用户看到再反应。

(3) **帮用户归位**——用户开始纠结细节时，提醒「这是 WHAT 还是 HOW 的问题」，帮其回到正确层级。

(4) **识别反复纠结**——同一处修改超过 2 次，主动总结矛盾点，问清到底在纠结什么。

(5) **每阶段结束输出完整文档快照**——不要只说「改了什么」，给完整版让用户确认全貌。

(6) **不替用户做产品决策**——但要提醒遗漏的场景或矛盾的逻辑。
