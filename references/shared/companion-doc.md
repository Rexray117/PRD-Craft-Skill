# 补充说明文档结构规范（共用层）

本文件定义与 PRD 正文配套的《补充说明文档》的六节结构。两个特化方向共用。

**使用前提**：与正文同时产出。正文不承载的一切杂项信息全部收入本文档，本文档是**唯一**的杂项出口。

**引用关系**（禁止复制以下内容到本文件）：

| 内容 | 引用位置 |
| :--- | :--- |
| 占位符双轨制、语言、编号体例、排版规则 | `conventions.md` |
| 通用门禁 G1–G10 | `quality-gate.md` |
| 指标表结构 | `metrics-spec.md` |

**目录层级**：`references/shared/companion-doc.md`

---

## 1. 六节总览

| 节 | 名称 | 承载内容 | 必选性 |
| :--- | :--- | :--- | :--- |
| 1 | 文档信息 | 名词解释、角色与读者、文档归属与章节对应 | 必选 |
| 2 | 需求背景 | 业务现状与痛点、目标用户与使用角色、需求目标与成功标准、参考资料 | 必选 |
| 3 | 待确认事项清单 | 需业务方决策项、需技术方确定项、正文留空位置对照 | 必选 |
| 4 | 版本变更说明 | 版本记录、本次变更明细、篇幅对照 | 必选 |
| 5 | 非核心需求细则 | 界面与文案规范、配置字段校验、容量估算、附加功能候选 | 按需 |
| 6 | 配套文档索引 | 配套文档清单、与其他版本的对应关系 | 必选 |

**文件头**：首行为文档标题 `# [产品名称] 产品需求文档（PRD）— 补充说明文档`，次行用引用块写明本文档定位与正文章节范围。

## 3. 第二节 需求背景

### 3.1 业务现状与痛点

| 项 | 内容 |
| :--- | :--- |
| 现状 | [当前用什么方式完成这项工作，写明可观测的现状事实] |
| 规模 | [涉及的对象数量、频率、人力投入，必须带数字] |
| 痛点 | [① 痛点一及其代价 ② 痛点二及其代价 ③ 痛点三及其代价] |
| 触发因素 | [为什么现在做] |

痛点必须写清「代价」——耗时多少、出错率多少、多久发现一次问题。无法量化时填 `[待补充：{痛点项}的量化口径]`。

### 3.2 目标用户与使用角色

| 角色 | 场景 | 当前如何解决 | 期望变化 | 使用频次 |
| :--- | :--- | :--- | :--- | :--- |
| [角色] | [在什么情况下需要] | [现在怎么做] | [做完后行为怎么变] | 每日 / 每周 / 按事件 |

**方向 A 特有**：目标用户须分两类列清——① **受益方**（Agent 替谁干活）② **操作方**（谁配置、谁审批、谁看报告）。

### 3.3 需求目标与成功标准

**需求目标**：1–3 条，必须可验证，描述行为变化而非功能名称。

> 反例：「提升运维效率」——不可验证。
> 正例：「把设备异常发现时机从人工巡检的 T+1 天缩短到 ≤ 3 分钟」。

**成功标准**：表结构见 `metrics-spec.md` §1 完整版 + §3 三层分层（北极星 1 + 辅助 1–2 + 护栏 0–1）。
